# Smarteam V2 Database Schema

**Status:** Proposed design for review — revision 2  
**Scope:** PostgreSQL schema for the backend and BlizBooks federation layer  
**Source documents:** [PRD.v1.md](./PRD.v1.md), [TECHSTACK.v1.md](./TECHSTACK.v1.md), [Phase-1.v1.md](../development/Phase-1.v1.md)

This document defines the relational model before the Prisma schema is finalized. It covers the native product, platform administration, multi-tenant isolation, attendance geofencing, teams and projects, component-based payroll, object storage metadata, and the compatibility surface required by BlizBooks.

The schema is intentionally shared-database and shared-schema. Every tenant-owned row carries `organization_id`, even when another foreign key already implies the organization. That duplication gives PostgreSQL RLS a direct policy key and lets the application detect cross-tenant relationship mistakes.

## 1. Design decisions

### 1.1 Identifiers and timestamps

- Primary keys use UUID values generated by PostgreSQL or the application.
- External identifiers from BlizBooks use `text`, not UUID. The existing integration must preserve identifiers even if BlizBooks uses numeric, composite, or non-UUID values.
- All timestamps use `timestamptz` and are stored in UTC.
- Business dates use `date` and are interpreted in the organization's timezone.
- Local clock values such as shift start and end use `time without time zone`.
- Money uses `numeric`, never floating point. Amounts are stored at the currency precision defined by the organization.
- JSON columns use `jsonb` and are reserved for versioned snapshots, extensible metadata, and event payloads. Core fields used for authorization, uniqueness, reporting, or joins remain relational columns.
- Mutable domain rows carry `created_at`, `updated_at`, and an integer `version` for optimistic concurrency where workflow races are possible.

### 1.2 Tenant ownership

Tenant-scoped tables are listed throughout Sections 4–14, and their RLS rules are defined in [Section 16](#16-rls-and-database-constraints). Their `organization_id` is mandatory and must be supplied to every domain-service operation.

The application sets these PostgreSQL transaction-local settings before querying tenant data:

```sql
SET LOCAL app.organization_id = '<organization uuid>';
SET LOCAL app.user_id = '<user uuid or empty string>';
SET LOCAL app.client_id = '<federation client uuid or empty string>';
SET LOCAL app.access_mode = 'NATIVE' | 'FEDERATION' | 'PLATFORM';
SET LOCAL app.platform_bypass = 'true' | 'false';
```

RLS policies compare `organization_id` with `current_setting('app.organization_id', true)::uuid`. Platform access uses an explicit, audited transaction path and never becomes a process-wide or connection-pool-wide bypass.

### 1.3 Deletion policy

Operational records are retained. Organization, employee, user, payroll, attendance, leave, federation, webhook, and audit rows are not physically deleted through normal APIs.

- Deactivation is represented by status and timestamps.
- Foreign keys use `RESTRICT` for financial, attendance, leave, payroll, and audit history.
- `CASCADE` is limited to join rows and ephemeral authentication/session records.
- S3 objects are soft-deleted in the database first. A background job applies the corresponding object-storage lifecycle action.
- A source change from `NATIVE` to `BLIZBOOKS`, or the reverse, is an explicit transaction recorded in `organization_source_changes`.

### 1.4 Ownership and provenance

`identity_source`, `source_access_mode`, and field ownership are different concepts:

- `identity_source` says who owns a human identity: native or BlizBooks.
- `source_access_mode` says how a mutation entered Smarteam: native application, federation API, or platform API.
- `employee_field_ownership` says which system may mutate a particular employee field.
- Federation scopes and grants authorize the BlizBooks application. They never replace Smarteam RBAC for a human employee.

### 1.5 Organization deactivation cascade (EC-8)

Deactivation is a deliberate, audited tenant lifecycle operation, not a database `DELETE` or an implicit foreign-key cascade:

- Set `organizations.status = DEACTIVATED` and `deactivated_at`, then write `organization_source_changes` only when the source also changes. The organization, settings, branches, employees, operational history, files, audit rows, and event history remain retained.
- Set active branches to `DEACTIVATED`. Active employee records are set to `INACTIVE` with `deactivated_at`; terminated employees remain `TERMINATED`. The audit entry preserves the pre-deactivation employee status for a deliberate reactivation workflow.
- Mark all `user_organizations` rows for the organization as `REMOVED` and set `removed_at`. Do not delete global `users`; set `users.is_active = false` only when the user has no other active organization membership and no platform role.
- Revoke all `auth_sessions` whose `organization_id` is the deactivated organization. A platform session or a session for another active organization is not revoked by this operation.
- Set active `federation_grants` for the organization to `SUSPENDED` with a deactivation reason. They cannot authorize requests while suspended; reactivation requires an explicit, audited platform operation rather than automatic restoration.
- Pause organization webhook subscriptions and stop creating new deliveries for that tenant. Existing outbox, delivery, attempt, and audit rows remain available for reconciliation.
- RLS and domain services reject new tenant operations once the organization is deactivated, except for the explicit platform reactivation/deactivation workflows.

Reactivation is also explicit and audited. It does not silently restore users, employees, grants, or subscriptions; each previously deactivated entity must pass its own lifecycle rules.

The API exposes an `owned_fields` object for employee records. The normalized `employee_field_ownership` rows are the source of truth behind that response.

## 2. PostgreSQL types and extensions

The first migration should enable:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS citext;
```

`pgcrypto` supports UUID and digest helpers where needed. `citext` supports case-insensitive email and login identifiers. If the hosting standard does not allow `citext`, store a normalized lowercase value in a separate `*_normalized` column and index that value instead.

## 3. Global identity and access tables

### 3.1 `users`

One human identity. A federation client is never stored as a user.

| Column                       | Type            | Null | Default             | Definition                                                     |
| ---------------------------- | --------------- | ---: | ------------------- | -------------------------------------------------------------- |
| `id`                         | `uuid`          |   No | `gen_random_uuid()` | Primary key.                                                   |
| `email`                      | `citext`        |   No |                     | Login and notification address.                                |
| `email_normalized`           | `text`          |   No |                     | Lowercase, trimmed canonical value for portable uniqueness.    |
| `display_name`               | `text`          |   No |                     | Name shown in the application.                                 |
| `password_hash`              | `text`          |  Yes |                     | Argon2 hash; null for federated-only identities.               |
| `identity_type`              | `identity_type` |   No | `NATIVE`            | Native or federated human identity.                            |
| `external_identity_provider` | `text`          |  Yes |                     | Provider key, initially `BLIZBOOKS`.                           |
| `external_identity_id`       | `text`          |  Yes |                     | Provider-owned user identifier.                                |
| `external_organization_id`   | `text`          |  Yes |                     | Provider tenant identifier for the primary federated identity. |
| `is_active`                  | `boolean`       |   No | `true`              | Login and session eligibility.                                 |
| `token_version`              | `integer`       |   No | `0`                 | Incremented to invalidate outstanding JWTs.                    |
| `last_login_at`              | `timestamptz`   |  Yes |                     | Last successful native or federated human login.               |
| `deactivated_at`             | `timestamptz`   |  Yes |                     | When the identity was deactivated.                             |
| `created_at`                 | `timestamptz`   |   No | `now()`             | Creation time.                                                 |
| `updated_at`                 | `timestamptz`   |   No | `now()`             | Last update time.                                              |

**Constraints and indexes**

- Unique on `email_normalized`.
- Unique on `(external_identity_provider, external_organization_id, external_identity_id)` when all three external values are present.
- A `NATIVE` user must have `password_hash` unless the account is invitation-pending.
- A `FEDERATED` user must not have a local password unless an explicit, audited conversion flow changes its identity type.
- A platform operator is assigned through `user_platform_roles`; platform role data is not stored in organization RBAC tables.

### 11.7 Payroll disbursement boundary

The current PRD scope ends at payroll calculation, approval, release, and payslip generation. This schema therefore does not store bank account numbers or initiate bank transfers. Before adding disbursement, explicitly decide the payment provider, supported countries/currencies, verification lifecycle, encryption/key ownership, beneficiary-change approvals, payment attempts, and reconciliation model. That future scope should introduce an `employee_bank_accounts` table and payment records in a separately reviewed design rather than placing sensitive banking data in `employees`, `payroll_line_items`, or `payslips`.

## 16. RLS and database constraints

Prisma models cannot express every required PostgreSQL safety rule. The migration set must include SQL for the following:

1. Enable RLS on every table with `organization_id`.
2. Add tenant policies for `SELECT`, `INSERT`, `UPDATE`, and `DELETE`, with normal application roles unable to bypass RLS.
3. Add a separate audited platform policy or stored procedure for cross-tenant support operations.
4. Add composite foreign keys or triggers ensuring `branch_id`, `employee_id`, `leave_type_id`, `timesheet_id`, `payroll_run_id`, `work_location_id`, `team_id`, `project_id`, and other related records belong to the same `organization_id`.
5. Add partial unique indexes for nullable external IDs on every synchronized domain table, plus active primary branch assignments, organization-wide holidays, and branch holidays.
6. Add check constraints for non-negative minutes, positive monetary quantities where required, valid date ranges, valid time ranges, and mutually exclusive audit actor columns.
7. Add exclusion constraints for effective-dated compensation, pay-component assignments, employment, team membership, shift, and branch assignment records where overlapping periods are invalid.
8. Add append-only permissions and trigger protections for `audit_logs`, `payroll_line_items`, `payroll_line_item_components`, `payroll_adjustments` after a run is locked, and `leave_balance_transactions`.
9. Add a trigger or transaction-level invariant that increments aggregate `version` values and rejects stale updates.
10. Add a trigger or service invariant that writes an `outbox_events` row in the same transaction as every externally observable domain mutation.

## 17. Federation compatibility contract

The schema must support the existing BlizBooks-facing endpoint families without requiring BlizBooks to change its integration model:

| Existing surface              | Primary tables                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `/v1/oauth/token`             | `federation_clients`, `federation_client_credentials`, `federation_scopes`                                                         |
| `/v1/federation/tenants/*`    | `organizations`, `organization_settings`, `branches`, `external_id_mappings`, `organization_federation_capabilities`               |
| `/v1/federation/employees/*`  | `employees`, `employee_branch_assignments`, `employee_field_ownership`, `user_organizations`, `user_roles`, `external_id_mappings` |
| `/v1/federation/attendance/*` | `attendance_records`, `attendance_punches`, `attendance_corrections`, `external_id_mappings`                                       |
| `/v1/federation/leave/*`      | `leave_types`, `leave_balances`, `leave_balance_transactions`, `leave_requests`, `leave_approvals`                                 |
| `/v1/federation/payroll/*`    | `timesheet_periods`, `timesheets`, `timesheet_entries`, `payroll_runs`, `payroll_line_items`, `payslips`                           |
| `/v1/federation/events`       | `outbox_events`, `webhook_subscriptions`, `webhook_deliveries`, `webhook_delivery_attempts`, `webhook_signing_keys`                |

The federation adapter must preserve:

- OAuth client-credentials authentication and token format.
- Optional mTLS verification at Nginx, with the verified certificate fingerprint passed to the API.
- HMAC-SHA256 request signing over the canonical method, path, body hash, actor, tenant, branch/outlet, target, and nonce.
- Replay rejection within the configured clock-skew and nonce window.
- Idempotency keys and canonical request hashes.
- Correlation IDs through request processing, outbox events, and webhook attempts.
- Additive-only request and response evolution.
- Stable external IDs for organizations, branches, employees, and other mapped entities.

The geofence, holiday, team, project, and dynamic payroll-component tables are native domain capabilities in this revision. They do not require new BlizBooks requests or response fields. If BlizBooks later needs any of them, expose them through a new capability and additive contract version rather than coupling their internal tables directly to the existing federation payloads.

Redis is the primary low-latency store for nonce replay records, short-lived access-token metadata, rate limits, and in-flight idempotency locks. PostgreSQL remains the durable source for grants, request evidence, idempotency results, audit, outbox events, and webhook delivery state.
