# Smarteam V2 — Technology Stack

**Status:** Approved for implementation
**Related documents:** Smarteam V2 Rewrite Plan, Smarteam V2 PRD

**Deployment note:** No containerization (no Docker/Kubernetes). Deployment follows the same model as BlizBooks/BhojAI — direct process deployment on managed servers.

---

## 1. Backend

| Component | Technology | Notes |
|---|---|---|
| Language | TypeScript | Strict mode enabled across the codebase |
| Framework | NestJS | Module structure maps directly to `employees/`, `attendance/`, `federation/*` domain boundaries |
| Runtime | Node.js (LTS) | Match the LTS version already used by BlizBooks/BhojAI where possible, for ops consistency |
| Process manager | PM2 | Process supervision, restarts, log management, cluster mode across CPU cores, zero-downtime reload |
| API style | REST | Matches existing BlizBooks federation contract; Application API follows the same style for consistency |
| Validation | class-validator + class-transformer | DTO validation at the controller boundary (NFR-3) |
| Shared contracts | Zod | Runtime-safe request, response, federation, event, and environment schemas shared across workspace packages |
| Config management | @nestjs/config + dotenv (per-environment `.env`, not committed) | Secrets pulled from secrets manager, not raw `.env` in production (see §7) |

## 2. Database

| Component | Technology | Notes |
|---|---|---|
| Primary database | PostgreSQL (latest stable LTS release) | Transactional integrity for payroll; `jsonb` support for `owned_fields` provenance |
| ORM | Prisma | Schema-first modeling, migrations, type-safe query client |
| Migrations | Prisma Migrate | Versioned, reviewed migration files checked into source control |
| Connection pooling | PgBouncer (or Prisma's built-in pooling if load is moderate) | Required once concurrent connections from multiple app instances (PM2 cluster mode) exceed Postgres's default connection limit |
| Backups | Scheduled `pg_dump` + WAL archiving, or managed Postgres backup if using a managed DB host | Point-in-time recovery required given payroll/financial data |

---

## 3. Object Storage

| Component | Technology | Notes |
|---|---|---|
| Object storage | AWS S3 | Store resumes, profile images, employee documents, payslip files, exports, and other user-uploaded or generated binary assets. |
| Access | AWS SDK for JavaScript v3 with server-generated presigned URLs | Keep buckets private; the API authorizes access before issuing short-lived upload/download URLs. |
| Encryption | S3 server-side encryption with AWS KMS (SSE-KMS) | Use managed keys per environment, with least-privilege IAM access for the API and background workers. |
| Organization isolation | Tenant-scoped object keys and authorization checks | Every object is associated with an organization and resource record; object paths are generated by the backend and never accepted as trusted client input. |
| Lifecycle and recovery | S3 lifecycle rules, versioning, and retention policies | Apply retention and cleanup policies by asset type; preserve compliance-sensitive documents according to the applicable retention requirement. |

Uploads must be validated for size, MIME type, extension, and content where required. The API must not expose bucket credentials, allow public bucket access, or trust client-supplied object keys. Upload metadata and ownership must be persisted in PostgreSQL so files remain auditable and removable without scanning the bucket directly.

## 4. Caching, Queues, and Background Jobs

| Component | Technology | Notes |
|---|---|---|
| In-memory store | Redis | Nonce/replay tracking, rate limiting, idempotency-key dedupe cache, session cache |
| Queue | BullMQ (Redis-backed) | Webhook delivery workers, retry with backoff, dead-letter handling, scheduled/reconciliation jobs |
| Job monitoring | Bull Board (BullMQ's dashboard UI) | Operational visibility into queue depth, failed jobs, retries — self-hosted, no extra infra |

## 5. Frontend

| Component | Technology | Notes |
|---|---|---|
| Framework | Next.js (React, TypeScript) | Native Smarteam application UI |
| Server state / data fetching | TanStack Query | Caching, invalidation, and loading/error states for RBAC-gated API calls |
| Styling | Tailwind CSS | Utility-first, fast to build consistent layouts |
| Component library | shadcn/ui | Composable, unstyled-by-default components — needed for custom states like "field managed by BlizBooks (read-only)" |
| Forms | React Hook Form + Zod | Form state + schema validation, shared validation shapes with backend DTOs where practical |
| Auth on client | HTTP-only cookies (session) or short-lived JWT + refresh, issued by the NestJS backend | No token storage in localStorage |

## 6. Authentication & Authorization

| Concern | Technology | Notes |
|---|---|---|
| Native user auth | Passport.js (NestJS integration) + JWT | Standard session/token issuance for native logins |
| Password hashing | argon2 | Stronger default than bcrypt for new systems |
| Federation (application) auth | Custom OAuth 2.0 client-credentials implementation | Built in-house — required anyway for custom signature/nonce/mTLS logic; no external IdP needed |
| RBAC | Custom NestJS Guards + a permissions module (roles/permissions tables) | Enforced at the domain-service layer per NFR-12, not only at the controller |
| Request signing | HMAC-SHA256, constant-time signature comparison | Matches existing BlizBooks federation signing scheme |
| mTLS | Terminated at the reverse proxy (Nginx), verified client cert forwarded to app via header | Keeps TLS termination out of application code |

## 7. Reverse Proxy / Web Server

| Component | Technology | Notes |
|---|---|---|
| Reverse proxy | Nginx | TLS termination, mTLS client cert verification, routing to PM2-managed Node processes, rate limiting at the edge as a first line of defense |
| TLS | TLS 1.2 minimum, TLS 1.3 preferred | Certificates via existing internal CA process or Let's Encrypt, consistent with BlizBooks/BhojAI's current setup |

## 8. Secrets & Configuration Management

| Component | Technology | Notes |
|---|---|---|
| Secrets storage | Cloud provider secrets manager (AWS Secrets Manager / GCP Secret Manager) or self-hosted Vault, matching whatever BlizBooks/BhojAI already use | DB credentials, client secret hashing keys, JWT signing keys, mTLS CA material — never committed, never in plain `.env` on the server |
| Environment separation | Distinct config per environment (local/staging/production) | Loaded via `@nestjs/config`, sourced from the secrets manager in staging/production |

## 9. Observability

| Component | Technology | Notes |
|---|---|---|
| Structured logging | Pino | JSON logs, fast, integrates cleanly with NestJS |
| Log aggregation | Existing centralized logging used by BlizBooks/BhojAI (e.g., ELK/OpenSearch, or a managed service) | Reuse existing infra rather than introducing a new logging stack |
| Tracing | OpenTelemetry, W3C Trace Context (`traceparent`) propagation | Satisfies correlation-ID requirement (NFR-18) with an interoperable standard |
| Metrics | Prometheus client (`prom-client`) exposing a `/metrics` endpoint, scraped by existing Prometheus/Grafana setup if available; otherwise a managed APM (Datadog) | Request rates, error rates, webhook delivery success/failure, replay attempts (NFR-19) |
| Uptime/health checks | NestJS Terminus module | `/health` endpoint for load balancer and process monitoring |
| Error tracking | Sentry (or existing error-tracking tool used by BlizBooks/BhojAI) | Backend and frontend exception capture |

## 10. Testing

| Layer | Technology | Notes |
|---|---|---|
| Unit tests | Jest | Default with NestJS; domain services tested independently of controllers |
| Integration tests | Jest + Supertest | Application API and Federation API endpoint-level tests |
| Contract tests | Jest-based suite built from captured real BlizBooks production request/response samples | Required before any federation endpoint is considered complete (per PRD §7) |
| E2E (frontend) | Playwright | Critical native user flows: login, employee CRUD, leave approval, payroll run |
| Load/replay testing | k6 or Artillery | Validate rate limiting, idempotency, and webhook throughput under load |

## 11. Deployment & Process Management

| Component | Technology | Notes |
|---|---|---|
| Deployment model | Direct deployment to managed servers (no containers) | Consistent with existing BlizBooks/BhojAI deployment approach |
| Process supervision | PM2 (cluster mode) | Multi-core utilization, auto-restart on crash, zero-downtime reload (`pm2 reload`) |
| Build artifacts | Compiled NestJS (`dist/`) and Next.js production build (`.next/`), deployed via GitLab CI pipeline (build stage → deploy stage, e.g., rsync/SCP over SSH to the target server + PM2 restart) | Reuse the existing BlizBooks/BhojAI GitLab Runner pipeline pattern rather than introducing a new deployment mechanism |
| CI/CD | GitLab CI/CD with GitLab Runner | Same pipeline mechanism already used for BlizBooks/BhojAI; `.gitlab-ci.yml` stages for lint, typecheck, unit + integration + contract tests, build, deploy |
| Environment consistency | `.nvmrc` pinning Node version, `package-lock.json` committed | Prevents version drift across dev/staging/production without needing containers |

## 13. Explicit Non-Choices

To avoid ambiguity for the team:

- **No Docker/Kubernetes** — deployment mirrors the existing BlizBooks/BhojAI server deployment model.
- **No external IdP (Keycloak/Auth0/Okta)** for federation auth — the custom signature/nonce/mTLS scheme required by the BlizBooks contract is bespoke enough that a generic IdP adds overhead without solving the actual problem.
- **No Kafka/SQS at launch** — BullMQ on Redis is sufficient for current webhook/event volume with a single federation client (BlizBooks); revisit only if event volume or number of federation clients grows substantially.
- **No GraphQL** — REST matches the existing federation contract and keeps the Application API consistent with it.
